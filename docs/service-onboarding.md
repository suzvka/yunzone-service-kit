# 业务节点接入规范（Service Onboarding）

> **文档版本**：v0.1（草案）
> **适用范围**：yunzone 集群全部**业务节点**（指依赖系统实例的、以产品为中心的部署单元，如 WanyanAI；系统实例指用户中心 / 鉴权中心）
> **设计日期**：2026-08-19

---

## 0. 目的

定义新增业务节点的标准接入路径，回答：
1. 业务节点如何「发现」系统实例（用户中心 / 鉴权中心）？
2. 业务节点如何获得并维护访问凭证（不再依赖人工长期维护静态 API Key）？

---

## 1. 现状：配置注入式接入（已具备）

**结论：当前已具备「平台注入 + 分面契约」的低成本接入能力，但这不是动态服务发现。**

### 1.1 依赖结构

- 业务节点不硬编码上游地址，通过 `yunzone-service-kit/config` 的分面契约读取（见 `authCenterFacet` / `userCenterFacet`）
- 上游 URL 由部署平台（Coze）注入，经 `deploymentAliases` / `normalizeDeployEnv` 在读取时回退映射到中立键（TICKET-001）

### 1.2 接入要素（现有）

| 变量 | 来源 | 说明 |
|---|---|---|
| `AUTH_CENTER_URL` | 平台注入 / 运维配置 | 鉴权中心地址 |
| `AUTH_CENTER_API_KEY` | 鉴权中心管理后台**人工签发** | 业务节点的 `sk-client-*` |
| `AUTH_CENTER_PRODUCT_ID` | 运维配置 | 隔离边界（产品唯一） |
| `USER_CENTER_URL` | 平台注入 / 运维配置 | 用户中心地址（如需嵌入登录） |

### 1.3 局限

1. `AUTH_CENTER_API_KEY` 需人工签发 + 人工保管，无自动轮换
2. 长期静态 key 泄露面大
3. 新增业务节点仍依赖管理员操作，未实现自助化

---

## 2. 目标态：自举兑换 + 自动轮换

### 2.1 凭证生命周期

```
┌─ 部署时（一次性，管理员操作）────────────────────────────────────┐
│ 管理员在鉴权中心管理后台签发 bootstrap secret（短效、限来源）        │
│   └─→ 写入部署配置：AUTH_CENTER_BOOTSTRAP_SECRET（一次性注入）      │
└─────────────────────────────────────────────────────────────────┘
                                │
┌─ 业务节点启动（自助，无人值守）───────────────────────────────────┐
│ POST /api/v1/client/token { bootstrapSecret, productId }         │
│   └─→ 换取短期 client credential（默认 24h）                       │
│   └─→ 仅存内存，不落盘；启动后由客户端自动续期                      │
│ 依赖注入的中立键（平台注入 → kit 分面契约）：                        │
│   AUTH_CENTER_URL        （系统实例地址，平台注入）                │
│   AUTH_CENTER_PRODUCT_ID （业务节点唯一标识）                      │
│   USER_CENTER_URL        （如需嵌入登录）                          │
│   DEPLOY_PROVIDER=coze   （启用平台注入别名回退）                  │
└─────────────────────────────────────────────────────────────────┘
                                │
┌─ 运行期 ────────────────────────────────────────────────────────┐
│ 权限解析：introspect（带内存中的短期 client credential）           │
│ 过期前自动 refresh —— API Key 自动轮换，无需人工运维               │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 新增业务节点完整接入清单

| # | 动作 | 操作方 | 前置依赖 |
|---|---|---|---|
| 1 | 确定唯一 `AUTH_CENTER_PRODUCT_ID` | 业务方 | 命名规范（产品标识） |
| 2 | 管理员签发 bootstrap secret | 鉴权中心管理员 | 鉴权中心新增 `/api/v1/client/token` |
| 3 | 注入 4 个中立键（`AUTH_CENTER_URL` / `AUTH_CENTER_PRODUCT_ID` / `USER_CENTER_URL` / `DEPLOY_PROVIDER`） | 平台 / 运维 | 平台注入能力（已具备） |
| 4 | 注入 bootstrap secret（一次性） | 平台 / 运维 | — |
| 5 | `pnpm add yunzone-service-kit` | 业务方 | kit 发布 |
| 6 | 启动即自动换取短期凭证 → 登录、权限、OAuth 全部就绪 | 自动 | kit `config` + 新凭证客户端 |

## 3. 鉴权中心需新增的能力

### 3.1 `POST /api/v1/client/token`（bootstrap 兑换端点）

- 入参：`{ bootstrapSecret, productId }`
- 出参：`{ credential, expiresAt, refreshToken }`
- 校验链：复用现有 `clients` 表与哈希校验（见 `yunzone_auth/src/lib/middleware.ts`），新增 bootstrap 凭证类型，**不破坏现有 `sk-client-*` 校验**

### 3.2 凭证自动续期客户端（放入 kit）

- 建议新增 kit 子路径（如 `yunzone-service-kit/authz`），业务节点一行接入：
  - 启动兑换
  - 到期前自动 refresh
  - 失败告警并回退「降级 / 熔断」策略

### 3.3 双轨兼容

- 存量 `AUTH_CENTER_API_KEY` 保持兼容：bootstrap 机制上线后，**新节点用自动凭证**，存量节点可平滑迁移（旧 key 在有效期内双轨并存）

---

## 4. 效益对照

| 维度 | 现状 | 目标态 |
|---|---|---|
| 凭证维护 | 人工签发 + 每节点环境变量保管 | 启动自助兑换 + 自动轮换 |
| 新增节点接入 | 手工签发 API Key + 人工配置 | 管理员签发一次性 bootstrap + 平台注入 URL |
| 泄密风险 | 长期静态 key 泄露面大 | 短期凭证 + 内存态 + 自动轮换 |
| 凭证吊销 | 管理后台手动操作 | bootstrap 短效自动失效；refresh 链路支持吊销 |

---

## 5. 关于「服务发现」的边界说明

本规范提供的是**「配置注入式接入」**（上游实例稳定、一实例稳态），其成立前提：

- 系统实例（用户中心 / 鉴权中心）暂为**单实例稳态部署**，由平台注入固定 URL 即可
- 业务节点数量可控，凭证签发未成为瓶颈

**触发升级到动态服务发现（Consul/Nacos 语义）的信号**：

1. 系统实例开始多副本 / 自动扩缩容（固定 URL 无法表达实例列表）
2. 业务节点数量增长到人工签发凭证成为瓶颈（应先补「凭证自动签发」，即本规范第 2 节）
3. 需要跨实例负载均衡与故障自动摘除

在信号出现前，**不建议引入服务注册发现组件**，保持「平台注入 + 分面契约」的简单结构。
